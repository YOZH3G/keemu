# KEEMU MVP 1 — техническое задание для реализации

**Редакция:** 2.2, 22 сентября 2026 года  
**Основание:** переработанный KEEMU_MVP1(1).md и техническая оценка его реализуемости.  
**Статус:** спецификация; реализация и экспериментальное подтверждение пока не выполнены.  
**Среда реализации:** терминал, доступ к репозиторию и Linux-хосту для испытаний. Выбор ИИ-модели, провайдера и усилия рассуждения выполняется самостоятельно и не задаётся этим ТЗ.  
**Целевой результат:** воспроизводимая среда проверки и интерактивного запуска Entware-приложений с универсальными сценариями приёмки.

## 1. Назначение и границы достоверности

KEEMU устанавливает пакеты, запускает программы нужной архитектуры, воспроизводит согласованный набор файлов и событий KeeneticOS и сохраняет доказательства выполненных проверок. Установленной программой можно пользоваться из браузера или сетевого клиента на рабочем компьютере.

KEEMU отвечает на вопрос:

> Прошёл ли этот артефакт заданный сценарий в указанном окружении Entware, с указанными подменами и возможностями ядра хоста?

Успешный результат не доказывает полную совместимость с физическим Keenetic. Для заключения о конкретной модели и версии KeeneticOS нужен отдельный контрольный прогон на устройстве.

### 1.1. Что выполняется реально

- Целевые ELF-программы и целевой shell под QEMU user-mode.
- Загрузчик, libc и библиотеки из закреплённого Entware feed.
- Установка и удаление через настоящий opkg.
- Скрипты жизненного цикла, init-скрипты и обработчики событий.
- Работа файловой системы, TCP/UDP-сокетов, HTTP/HTTPS и сохранение настроек.
- В сетевом режиме — передача пакетов между клиентом, маршрутизатором и сервером.

### 1.2. Что моделируется или остаётся ограничением

- NDM: только перечисленные команды, ответы и события, подтверждённые образцами.
- Модель устройства: метаданные и наблюдённые особенности, а не эмуляция SoC.
- Ядро: используется Linux хоста. Версия в профиле не меняет его поведение.
- Модули Keenetic, драйверы Wi-Fi, аппаратный NAT, switch ASIC и модемы не воспроизводятся.
- Производительность, задержки и пропускная способность QEMU не характеризуют роутер.
- Локальный сетевой тест не доказывает эффективность обхода ограничений у провайдера.

**Обязательное правило:** реальная проверка, моделирование и отсутствие проверки всегда различаются в отчёте. Нельзя превращать неизвестную команду, отсутствующее ядровое API или пропущенный тест в PASS.

## 2. Объём и последовательность поставки

Исходная многоархитектурная цель сохранена. Разработка разделена на принимаемые этапы, чтобы получить полезное приложение раньше всей матрицы.

| Поставка | Обязательный результат | Что ещё не подтверждено |
|---|---|---|
| P0: технические эксперименты | Целевой shell и opkg; веб-сервис; проверка NFQUEUE; контракты тестовых приложений | Полнота CLI и поддержка устройств |
| MVP 1A: основа | AArch64, IPK lifecycle, отчёты, persistent runtime, TCP/UDP, веб-панель образцового пакета | Полная матрица и обработка трафика |
| MVP 1B: совместимость | MIPSEL/MIPS, матрица артефактов, строгий NDM shim, подтверждённые события | Полная проверка сетевых сценариев |
| MVP 1C: целевой сценарий | Тестовое сетевое приложение, панель, backend, сохранение настроек, тест обработки трафика | Эквивалентность физическому Keenetic |

**MVP 1 завершён только после 1A, 1B и 1C.** Если сетевой эксперимент заблокирован, можно поставить 1A как самостоятельный результат, но нельзя объявлять весь MVP готовым.

Для 1C обязательно подтверждение обработки трафика на AArch64. На MIPSEL/MIPS обязательны общие self-tests и зафиксированный результат сетевого capability probe; сетевые возможности этих архитектур объявляются поддержанными только после собственного успешного испытания.

### 2.1. Не входит в MVP 1

Полная загрузка прошивки; firmware importer; Keenetic SDK integration; QEMU full-system; собственные патчи QEMU без отдельного решения; точная эмуляция старого ядра; Wi-Fi; аппаратное ускорение; реальное USB-устройство; полноценный NDMS; Web UI самого Keenetic; облачный сервис; GUI KEEMU; Kubernetes; автоматическое управление физическим роутером.

Podman, Debian, Windows/WSL2, Docker Desktop, прямой LAN-доступ, multicast между хостом и стендом, автогенерация device profiles и массовая ферма роутеров — следующие этапы. Документ не заявляет их проверенную поддержку.

## 3. Зафиксированные решения

| Область | Решение для MVP |
|---|---|
| Хост | Linux x86_64, Ubuntu 24.04 LTS; bare metal или VM с управляемым ядром |
| Контейнеры | Один backend: Docker Engine; вызовы из Python через argv, без shell-конкатенации |
| Оркестратор | Python 3.12, Click, PyYAML, Pydantic; Rich только для терминального вывода |
| Исполнение | QEMU user-mode + binfmt_misc; QEMU фиксируется вместе с образом |
| Корень приложения | Отдельный OCI-образ для каждого Entware target |
| Системный shell | Целевой BusyBox ash в /bin/sh, совместимый с выбранной архитектурой |
| Управление контейнером | Нативный статический init и минимальные служебные утилиты в /__keemu; вне PATH приложения |
| Сетевой стенд | Три контейнерных network namespace: client, router, server |
| Первый firewall backend | iptables-legacy при подтверждённой доступности; иной backend требует отдельной записи |
| Состояние | Сохраняемый контейнер; down останавливает, destroy удаляет |
| Изоляция автотестов | Новый writable layer на каждый run; базовый образ неизменяемый |
| Версии | Общий lock-файл: OCI digest, QEMU, feed и IPK-хеши, сценарий, профиль, версии проверяемых приложений |
| Отчёты | JSON — источник данных; Markdown генерируется из того же объекта |

Выбор native init не означает запуск приложения на x86_64. Все shell-команды пакета, opkg и backend исполняются в целевом окружении. Нативные утилиты управления перечисляются в отчёте и исключаются из проверки ELF приложения.

Точные версии зависимостей, хеши и commit SHA заполняются по реально полученным артефактам на P0. Нельзя выдумывать версии для формального заполнения lock-файла.

## 4. Архитектура исполнения

Python CLI управляет Docker с хоста. У каждого router-контейнера собственные mount, PID и network namespace. Корень контейнера содержит target rootfs, Entware в /opt и небольшой каталог /__keemu с нативным init и служебным процессом, поддерживающим контейнер работающим.

Практический вариант PID 1: закреплённый статический tini, запускающий статический keepalive-процесс. Init должен передавать сигналы и собирать завершившиеся дочерние процессы. На P0 проверяется, что демоны, запущенные через docker exec, продолжают работать после завершения init-скрипта, а остановка окружения завершает их.

OCI metadata и выбор platform должны соответствовать фактически нативному entrypoint. Для предложенной схемы образ запускается как linux/amd64, а целевая архитектура приложения хранится отдельно в labels и профиле. Нельзя полагаться на автоматический выбор platform Docker для определения архитектуры Entware. На P0 проверить этот смешанный образ и исключить случайный запуск x86_64-версии приложения.

Команды приложения запускаются через docker exec с заданными cwd, PATH и окружением. В штатном режиме внутри контейнера не создаётся дополнительный network namespace: иначе обычный Docker publish не попадёт в сокеты приложения.

### 4.1. Требования к rootfs

Минимальные каталоги: /bin, /sbin, /etc, /lib, /usr, /opt, /tmp, /run, /var, /root. /proc, /sys и /dev предоставляет OCI runtime с его стандартными ограничениями. Не подменять содержимое /proc случайными снимками с роутера.

Обязательно обеспечить:

- Рабочий целевой /bin/sh и штатный PATH Entware.
- Настоящие opkg, загрузчик и зависимости выбранного target.
- Корректные passwd/group, разрешение localhost и контейнерный DNS.
- CA bundle для HTTPS; локальная тестовая CA устанавливается только в тестовый trust store.
- Доступные /dev/null, /dev/zero, /dev/urandom; терминал для shell при необходимости.
- Требуемые права и symlink; абсолютные ссылки разрешаются внутри rootfs.
- Исполнимый bootstrap, не зависящий от ещё не установленной целевой библиотеки.

Использовать реальные имена пакетов из закреплённого feed. Перечень «busybox/libc/libgcc/ca-certificates» из исходного ТЗ задаёт необходимые функции, но не гарантирует точное имя каждого пакета.

### 4.2. Binfmt и QEMU

Doctor проверяет регистрацию каждой нужной архитектуры и фактический запуск ELF внутри контейнера. Параметры регистрации, включая поведение interpreter fix-binary, документируются и сохраняются. Работоспособность binfmt проверяется вложенным сценарием: shell → дочерняя ELF → shell-скрипт с shebang.

Binfmt — настройка хоста. KEEMU не должен молча перезаписывать чужую регистрацию. Init проверяет её и выдаёт конкретную команду подготовки; изменение выполняется отдельным явным действием оператора. Пригодность уже установленной регистрации определяется тестом, а не только существованием файла.

Вызов qemu-ARCH -L ROOTFS PROGRAM допустим как диагностический эксперимент. Он не заменяет контейнер, полноценный rootfs и корректное исполнение дочерних программ.

### 4.3. Нативные диагностические инструменты

ss, ip, tcpdump и инструменты firewall можно выполнять нативным диагностическим процессом в network namespace тестового router-контейнера. Эти процессы создаёт оркестратор; пакет не получает Docker socket или интерфейс управления хостом.

Их результаты описывают ядро и сеть стенда. Если приложение использует нативный адаптер iptables, это явная подмена, а не проверка его собственного iptables-бинарника. Внутри /bin и /opt нельзя незаметно смешивать случайные x86_64-бинарники с target-окружением.

## 5. Профили архитектур и устройств

Поддерживаемые Entware targets: aarch64-3.10, mipsel-3.4, mips-3.4. Соответствующие QEMU: qemu-aarch64, qemu-mipsel, qemu-mips. Для MIPS дополнительно проверять endianness, ELF class, ABI и требования ISA/FPU.

Разделить два типа профилей:

1. **Generic:** воспроизводимое окружение конкретного Entware target. Не заявляет модель Keenetic.
2. **Device overlay:** наблюдения для определённой модели и версии KeeneticOS, накладываемые на generic.

Пример generic-профиля — валидный проектный формат; реализатор создаёт и валидирует его схему:

```yaml
schema_version: 1
id: generic-aarch64
revision: 1
kind: generic
entware_target: aarch64-3.10
cpu:
  arch: aarch64
  endian: little
  elf_class: 64
  qemu: qemu-aarch64
kernel:
  execution: host
  reported_release: null
filesystem:
  entware_root: /opt
ndm:
  mode: strict
  fixtures: []
network:
  logical_to_linux:
    ISP: wan0
    Bridge0: br0
```

Для device overlay обязательны: источник наблюдений, дата, модель, версия KeeneticOS, базовый target, использованные снимки и список неподтверждённых свойств. Пример KN-1812 из исходного документа не считается доказательством архитектуры, версии ядра или путей.

KN-1010, KN-1812 и KN-2410 остаются кандидатами. До сбора данных они имеют статус draft и не входят в заявленную поддержку. Отсутствие физического устройства не блокирует generic-профили.

### 5.1. Источники для device overlay

Оператор предоставляет только нужные сведения: вывод uname, фактическую архитектуру ELF и настройки opkg, show version в используемом формате, перечень NDM hook, наблюдённые переменные событий и соответствие логических/Linux-интерфейсов. Не запрашивать полный конфиг с паролями и ключами.

Подмена uname в shell не влияет на прямой системный вызов uname из программы. Любая такая подмена должна иметь отдельный тест и отражаться в отчёте. Отдельно фиксируются host_kernel_release, target_reported_release и источник последнего.

## 6. Пакеты и сценарии

### 6.1. Входные форматы

- Один локальный .ipk: inspect/install и ограниченный общий lifecycle.
- Scenario YAML: полная проверка конкретного приложения.
- Matrix YAML: сопоставление профилей и архитектурных артефактов.
- Pinned installer: локальный установочный сценарий с зафиксированными входами, для приложений, которые не поставляются как .ipk.

При отсутствии сценария KEEMU не угадывает главный бинарник и не запускает все исполнимые файлы пакета. Установка проверяется, а app-specific runtime отмечается SKIP с причиной.

### 6.2. Проверки IPK

Поддержать фактически встречающиеся в выбранном feed варианты внешнего контейнера IPK; определить формат по сигнатуре. Не предполагать, что каждый IPK обязательно имеет один и тот же ar/tar wrapper. Проверять control/data архивы и debian-binary там, где это предусмотрено распознанным форматом.

Проверки: корректность метаданных, Architecture, Depends, preinst/postinst/prerm/postrm, ELF machine/class/endian/ABI, PT_INTERP, DT_NEEDED, shebang, права и ссылки. Для зависимостей использовать readelf или парсер ELF и разрешение путей в target rootfs. Не выполнять host ldd над недоверенными файлами.

Проверка структуры проводится до установки в отдельной ограниченной среде. Не извлекать недоверенный архив в каталог проекта: отклонять выход через .., абсолютные пути вне правил формата, выход через ссылки, недопустимые special files; ограничивать число файлов и распакованный размер.

Hardcoded paths — предупреждения с контекстом. Отсутствующий интерпретатор или обязательная библиотека — FAIL после учёта устанавливаемых зависимостей. Создаваемая в postinst ссылка не должна ложно проваливать предварительную проверку: статическое замечание подтверждается после установки.

### 6.3. Scenario YAML

Пример для собственного fixture; имена, пути и API ниже относятся только к web-demo:

```yaml
schema_version: 1
id: web-demo
profile: generic-aarch64
install:
  kind: ipk
  path: ../packages/web-demo_aarch64.ipk
  package_name: web-demo
service:
  start: [/opt/etc/init.d/S80web-demo, start]
  stop: [/opt/etc/init.d/S80web-demo, stop]
  readiness:
    kind: http
    url: http://127.0.0.1:8080/health
    expected_status: [200]
    body_contains: keemu-web-demo
    timeout_seconds: 30
runtime:
  env: {}
  cwd: /opt
  settle_seconds: 2
  publish:
    - host_ip: 127.0.0.1
      host_port: 18080
      target_port: 8080
      protocol: tcp
requirements:
  capabilities: []
  ndm_fixtures: []
checks:
  - id: health
    kind: http
    vantage: target_loopback
    url: http://127.0.0.1:8080/health
    expected_status: [200]
    body_contains: keemu-web-demo
persistence:
  paths: [/opt/etc/web-demo/config.json]
cleanup:
  allowed_residual_paths: [/opt/etc/web-demo/config.json]
```

Все пути относительно каталога scenario, если не абсолютные. Команды задаются argv-массивами; shell разрешается только как явный /bin/sh -c с текстом доверенного сценария. Непонятные поля, повторные YAML-ключи и неизвестная версия схемы отклоняются. Обязательные значения не подставляются из догадок.

Расширения схемы: события, API-запись/чтение настройки, диагностические команды, ожидаемые файлы, сценарий остановки и список необходимых kernel capabilities. Секреты задаются через явные переменные, не хранятся в scenario или отчёте.

### 6.4. Матрица

```yaml
schema_version: 1
id: hello-matrix
cases:
  - profile: generic-aarch64
    scenario: scenarios/hello-aarch64.yaml
  - profile: generic-mipsel
    scenario: scenarios/hello-mipsel.yaml
  - profile: generic-mips
    scenario: scenarios/hello-mips.yaml
```

Каждый сценарий указывает свою сборку одного логического пакета. Общий Architecture: all допускается, если содержимое и загрузки действительно совместимы с каждым target.

Команда test package.ipk --all не преобразует бинарники: выполняется анализ применимости; несовместимые профили отмечаются SKIP/architecture-mismatch. Такой запуск не доказывает прохождение полной матрицы. Для релизной приёмки использовать --matrix и --strict.

### 6.5. Контракт pinned-installer

Для install.kind = pinned-installer обязательны entrypoint (argv), source_lock (ссылка на запись артефакта), working_directory и timeout_seconds. Source lock содержит происхождение, точный commit/release и SHA-256 локального bundle. Проверка целостности выполняется до запуска; bundle передаётся read-only, рабочая копия создаётся внутри контейнера.

Scenario обязан содержать verify_install и uninstall в виде argv-команд или поддержанного декларативного check. Наличие shell-установщика не означает наличие opkg-записи: такую установку учитывать отдельным типом. Для удаления вызывать закреплённый штатный uninstall; если его нет, явно описать adapter удаления и его ограничения. Удаление всего контейнера не заменяет проверку uninstall.

Служебные параметры адаптера приложения заполняются после inventory. Если неизвестны реальные команды или API, сценарий хранится как draft и не проходит schema validation для test/up. Нельзя заполнять неизвестные поля правдоподобными именами.

## 7. Entware bootstrap и воспроизводимость

Bootstrap выполняется при подготовке базового образа. Каждый тест получает новый слой и не изменяет образ. Контейнеры не собирают Entware с нуля при каждом запуске.

Порядок:

1. Получить индекс feed и необходимые bootstrap-артефакты.
2. Закрепить версии и SHA-256 всех реально используемых пакетов, включая транзитивные зависимости.
3. Создать минимальный rootfs и исполнить opkg в целевом окружении.
4. Установить необходимый базовый набор; сохранить opkg list-installed и конфигурацию feed.
5. Запустить вложенный exec smoke-test и DNS/HTTPS-проверку.
6. Собрать образ и записать его content digest в lock-файл.

Текущий публичный URL Entware не считается неизменяемым snapshot. Если snapshot недоступен, сохранить минимальное локальное зеркало нужных IPK, индекс и хеши. Индекс без самих пакетов не обеспечивает воспроизводимость.

В режиме --locked отсутствующий артефакт — ошибка подготовки. Нельзя незаметно заменить его latest или другой версией. Обновление lock выполняется отдельной командой и отдельным изменением репозитория.

Init может использовать Интернет для подготовки. Test и up по умолчанию требуют lock и используют закреплённые артефакты; получение ещё не кешированных файлов допускается только с проверкой ожидаемого hash. Незакреплённые интерактивные эксперименты требуют явного --unlocked и получают WARN/non-reproducible.

Автотесты образцовых пакетов после подготовки должны работать без Интернета. Для приложений с внешними загрузками предусмотреть локальный набор закреплённых загрузок или документированный adapter источников. Изменение upstream-установщика требует патча с явным учётом; тест такой версии не объявляется проверкой неизменённого upstream.

## 8. Установка и жизненный цикл

Основной pipeline:

1. Проверка схемы, артефактов, lock и возможностей окружения.
2. Статический анализ.
3. Создание чистого окружения и начальный filesystem snapshot.
4. opkg install либо закреплённый installer.
5. Проверка exit code, состояния opkg, файлов и журналов установки.
6. Проверка, не запущен ли сервис установщиком; при необходимости запуск по scenario.
7. Readiness и app-specific checks.
8. Явно перечисленные события и повторная проверка состояния.
9. Остановка; проверка завершения процессов и закрытия ожидаемых сокетов.
10. Удаление пакета; проверка допустимых остатков.
11. Сохранение отчёта и гарантированное удаление временных ресурсов.

postinst выполняет opkg. KEEMU не вызывает его второй раз. В отчёте сохраняются свидетельства и результат конфигурации opkg; если отдельный код postinst невозможно достоверно выделить, нельзя выдумывать его. Собственный fixture проверяет однократность счётчиком.

Событие boot и service start не дублируются в основном сценарии. Повторный boot/start/netfilter — отдельная проверка идемпотентности с явно указанным ожиданием.

Не у каждого пакета есть daemon, pidfile или команда status. Readiness определяется сценарием; одного наличия процесса недостаточно. Штатное завершение CLI-утилиты не считается failed startup.

Минимум MVP: install/start/stop/remove и сохранение настроек при перезапуске окружения. Upgrade с предыдущей версии и широкая матрица reinstall — следующий этап; повторная установка собственного fixture допустима как диагностический тест.

## 9. NDM shim и события

Shim реализует только команды, необходимые закреплённым сценариям. Для каждой команды хранить argv, stdout, stderr, exit code и источник образца. Поддержать реальные используемые способы вызова, включая ndmc -c, если они встретились.

По умолчанию strict: неизвестный вызов возвращает ненулевой код и событие unsupported-ndm-command. Если из-за него прервался обязательный тест, результат BLOCKED с причиной environment-gap. Нельзя автоматически считать виноватым пакет.

Команды чтения могут использовать fixtures. Поддерживаемые команды изменения состояния обязаны менять модель состояния shim и влиять на последующие чтения. Ответ exit 0 без какого-либо предусмотренного эффекта запрещён.

### 9.1. Event contract

Каждое событие описывает:

- Источник: synthetic либо observed с моделью/версией.
- Каталог и правило выбора обработчиков, argv, cwd, PATH и переменные.
- Порядок, timeout, обработку неисполняемых файлов и политику продолжения при ошибке.
- Состояние до/после события и ожидаемый эффект.

Список кандидатов: boot, netfilter, interface-up/down, usb-add/remove. В generic-профиле сначала обязательны synthetic boot и подтверждённый для сценария netfilter. USB/fd/interface hooks не объявляются достоверными только по названию каталога; до подтверждения контракта — unsupported.

Для netfilter фиксировать используемые type/table и другие фактически требуемые переменные. Для сценария восстановления правил: создать исходные цепочки, применить hook, изменить только тестовые правила, повторить событие и проверить восстановление без дубликатов. Очистка firewall хоста запрещена.

Логи ndmc и событий — JSONL с timestamp, run_id, argv/env allowlist, exit code, длительностью и ссылкой на fixture. Не записывать секреты из произвольного окружения.

## 10. Сетевой стенд и NFQUEUE

### 10.1. Топология

| Узел | Интерфейс и адрес по умолчанию | Назначение |
|---|---|---|
| client | LAN, 192.168.50.2/24 | Генерация тестового трафика |
| router | br0, 192.168.50.1/24 | LAN-шлюз; br0 создаётся как реальный Linux bridge |
| router | wan0, 10.10.10.2/24 | WAN-интерфейс |
| server | WAN, 10.10.10.1/24 | Локальные TCP/UDP/DNS/HTTP/HTTPS endpoints |

LAN-порт router подключён к br0. На client задан default route через router; на server — обратный маршрут к LAN через router. В router включён forwarding внутри его namespace. NAT добавляется только для отдельного сценария, которому он нужен.

Связи создаются отдельными внутренними Docker-сетями либо veth. На P0 выбрать один способ, описать его в ADR и использовать последовательно. Отдельная management-сеть предназначена для управления и host port publishing. Тестовый client не должен иметь обходного маршрута к server через management-сеть.

Адреса — defaults сценария, а не глобально зарезервированные сети. Перед запуском проверять пересечения маршрутов и выделять непересекающиеся подсети для параллельных run. Все ресурсы имеют run_id и labels принадлежности KEEMU.

### 10.2. Уровни сетевой достоверности

- **S0, rules-mock:** фиксируются вызовы firewall; реальная фильтрация не подтверждается.
- **S1, native-kernel-network:** реальные правила и пакеты, но firewall утилита может быть нативной адаптацией.
- **S2, target-network:** целевой сетевой процесс работает под QEMU и участвует в обработке пакетов; отдельно указывается происхождение управляющего firewall инструмента.

Уровни не взаимозаменяемы. S1 не доказывает совместимость целевого iptables; S2 не доказывает эквивалентность ядру Keenetic.

### 10.3. Capability probe

Doctor выполняет только чтение и проверку запуска без сетевых мутаций; наличие записей о модулях не подтверждает capability. Активный capability probe выполняется отдельной стадией test/P0 в одноразовых namespace.

Проверять на каждой архитектуре и версии окружения:

- Доступность выбранного iptables backend и необходимых extensions.
- Создание и удаление собственного ipset; совместимость версии протокола.
- Conntrack, forwarding, raw sockets при необходимости.
- Поддержку NFQUEUE ядром и создание очереди целевым процессом.
- Получение пакета, декодирование, возврат verdict и дальнейшее прохождение пакета.

Наличие модуля в lsmod или правила NFQUEUE недостаточно. В generic-network режиме insmod/modprobe пакета не получают права загружать модули хоста. Нужные модули заранее готовит оператор; KEEMU проверяет возможности.

### 10.4. Ранний эксперимент NFQUEUE

До большой реализации CLI выполнить на AArch64:

1. Контрольный TCP-запрос client → server без очереди.
2. Запуск маленького целевого queue-consumer, собранного с закреплённым toolchain.
3. Постановка тестового потока в выделенную очередь.
4. Подтверждение получения пакетов счётчиком consumer и возврата ACCEPT.
5. Подтверждение успешного запроса и соответствующих kernel counters.
6. Режим DROP: запрос перестаёт проходить; возврат ACCEPT восстанавливает его.
7. Завершение consumer и проверка заранее выбранного поведения очереди без слушателя.
8. Затем проверить управляемое переключение ACCEPT/DROP через API тестового сетевого приложения network-demo.

Не использовать queue-bypass в положительном тесте: трафик не должен проходить только потому, что consumer не работает. Сохранять pcap для локального тестового потока, счётчики, stdout/stderr и версии.

Если эксперимент не проходит: сначала отделить отсутствие возможности ядра от ошибки преобразования ABI/Netlink и от ошибки приложения. Сравнить с нативным consumer в том же namespace. Зафиксировать вывод; не тратить неопределённое время на обход. После двух обоснованных вариантов и одного контрольного native-теста оформить блокер и продолжить независимый MVP 1A.

## 11. Интерактивный запуск и веб-панели

```bash
keemu up --scenario fixtures/scenarios/web-demo.yaml --name demo
keemu status demo
keemu ports demo
keemu logs demo --follow
keemu shell demo
keemu down demo
keemu up --name demo
keemu destroy demo
```

Новый up создаёт окружение и устанавливает приложение один раз. Повторный up --name запускает существующее окружение без переустановки. Попытка незаметно заменить его scenario/profile/артефакт отклоняется; для другой версии создаётся новое окружение.

Down штатно останавливает сервисы и контейнер, сохраняя writable layer. Destroy удаляет только выбранное окружение и его состояние. Базовый образ и чужие окружения не затрагиваются. Restart = штатная остановка и запуск того же окружения. Для CLI без терминала destroy требует --yes; удаление — явная команда пользователя, а не шаг обычного up/down.

При перезапуске хоста Docker restart policy по умолчанию no. Автозапуск — последующее расширение. MVP не обещает сохранность состояния после ручного docker rm или потери диска.

### 11.1. Порты

```bash
keemu up --scenario fixtures/scenarios/web-demo.yaml \
  --name demo --publish 18080:8080/tcp
```

По умолчанию host_ip = 127.0.0.1. TCP и UDP задаются явно; несколько --publish допустимы. Конфликт порта выявляется и объясняется. Проверка bind до запуска не устраняет гонку: ошибку runtime тоже обработать с очисткой созданных ресурсов.

Обнаруженные listening sockets показываются отдельно от опубликованных портов. Автоматическая публикация всех найденных портов запрещена. Порты фиксируются при создании контейнера; изменение требует явного пересоздания или отдельного proxy, которого в основном MVP нет.

Если приложение слушает только container loopback, обычный publish не работает. Сначала использовать штатную настройку bind приложения. Если это невозможно, применить явно объявленный TCP/UDP proxy в том же namespace с отдельным тестом; показать его в отчёте. Публичную доступность не включать автоматически.

### 11.2. Проверки панели

HTTP smoke проверяет соединение, ожидаемый status, маркер содержимого и оговорённые redirect/auth. Наличие произвольного HTML или ответа 200 недостаточно: это может быть страница ошибки. HTTPS-проверка проверяет цепочку доверия и имя сервера; --insecure не закрывает критерий HTTPS.

Для fixture обязательны HTTP и HTTPS с локальной доверенной CA, а также UDP echo. Для стороннего приложения проверяется протокол, который предоставляет его закреплённая версия; HTTPS через отдельный frontend считается отдельным компонентом.

Readiness HTTP должна проверять endpoint в правильной точке наблюдения: target_loopback внутри router namespace, host_publish с Docker-хоста, client из тестового LAN. URL 127.0.0.1 без vantage не принимается в scenario: он неоднозначен. Для каждой проверки хранить фактический адрес и vantage.

Функциональная приёмка: получить состояние → изменить безопасную настройку через API/форму → прочитать её → перезапустить сервис и окружение → снова прочитать → подтвердить изменение поведения, если оно предусмотрено сценарием.

Автоматизация браузера не обязательна. Использовать HTTP API для воспроизводимой проверки; приёмка ручной формы фиксируется отдельно и не маскируется как automated PASS.

keemu open, hostname *.keemu и --lan-access перенесены за MVP. CLI всегда печатает фактический URL. Если Docker-хост удалённый, его 127.0.0.1 не является localhost компьютера пользователя; документировать SSH-туннель без автоматического открытия сервиса наружу.

## 12. Универсальное тестовое сетевое приложение

Для сквозной приёмки MVP 1C создать собственный fixture network-demo. Приёмка KEEMU не должна зависеть от наличия или особенностей конкретного стороннего проекта.

Network-demo содержит целевой NFQUEUE consumer, небольшой HTTP API и простую веб-страницу управления. Он позволяет прочитать состояние, переключить режим ACCEPT/DROP для выделенного тестового потока, увидеть счётчики и сохранить выбранный режим в конфигурации. Это тестовый инструмент; развитый интерфейс и функции промышленного маршрутизатора не требуются.

Использовать consumer из эксперимента P0, а не создавать вторую независимую реализацию. Web-demo остаётся лёгким fixture для HTTP/HTTPS и публикации портов без сетевых capabilities. Network-demo проверяет связь панели, backend и фактической обработки трафика.

Зафиксировать в scenario:

1. Версию, сборочный рецепт, архитектуру и зависимости fixture.
2. Команды установки, запуска, остановки и удаления.
3. Адреса API, bind/port и формат безопасной настройки режима.
4. Выделенный поток, номер очереди, правила и ожидаемые счётчики.
5. Пути конфигурации, проверку сохранения и допустимые остатки после удаления.

Приёмка делится на четыре независимых результата: install, web/API, persistence, packet-processing. Сначала подтвердить чтение и изменение режима через API, затем прохождение либо блокирование соответствующего локального потока. После перезапуска сервиса и окружения подтвердить сохранение режима и его применение. Управляющее соединение и health endpoint не должны попадать под тестовое DROP-правило.

Сторонние Entware-приложения подключаются отдельными scenario по тем же контрактам. Их сервисы, порты, команды NDM и способ установки определяются по фактическим данным. Поддержка pinned-installer остаётся универсальной возможностью для приложений без IPK. Особенности отдельного проекта не становятся обязательными требованиями ко всему MVP.

Если приложению необходим неподдержанный NDM или модуль ядра, соответствующая проверка получает BLOCKED с объяснением. Адаптированный сценарий фиксирует подмены и не выдаётся за проверку штатной интеграции.

## 13. CLI и контракты

| Команда | Назначение |
|---|---|
| doctor [--profile ID] | Read-only проверка хоста, Docker, binfmt и capabilities |
| init --profile ID | Подготовка кеша, rootfs, образа; без скрытой установки ПО на хост |
| profiles | Generic/device, revision, draft/verified |
| inspect PACKAGE | Статическая проверка без установки |
| test PACKAGE --profile ID | Ограниченный общий lifecycle |
| test --scenario FILE [--strict] | Полный сценарий |
| test --matrix FILE [--strict] | Матрица закреплённых сценариев |
| up --scenario FILE --name NAME | Создание persistent environment |
| up --name NAME | Запуск существующего environment |
| install NAME PACKAGE | Явная дополнительная установка в существующее окружение |
| exec NAME -- COMMAND… | Команда в целевом окружении |
| shell NAME | Интерактивный целевой shell |
| event NAME EVENT [--payload FILE] | Событие по контракту профиля |
| service NAME SERVICE ACTION | Только сервис, описанный в scenario |
| status / ports / logs NAME | Состояние, сокеты, публикации, журналы |
| down / restart / destroy NAME | Управление жизненным циклом |
| clean --runs | Удаление завершённых временных run KEEMU |

Для MVP нет дублирующей команды run: используется exec. Все команды с окружением требуют имя; не выбирать случайное «последнее». Имена, profile ID и пути валидируются; значения не попадают в shell-строки.

Внутренний сетевой setup управляется scenario, а не отдельным ручным обязательным net up. Диагностические низкоуровневые команды добавляются только при реальной необходимости.

Каждая операция должна быть ограничена по времени. Defaults: install 300 с, команда 60 с, readiness 30 с, shutdown 20 с; scenario может менять их. Истечение timeout сохраняет частичный отчёт, затем выполняется cleanup. Повтор теста допускается для диагностики, исходная неудача не стирается.

## 14. Результаты, exit codes и отчёт

### 14.1. Статусы

| Статус | Значение |
|---|---|
| PASS | Конкретное ожидание проверено и выполнено |
| WARN | Проверка выполнена, найдено некритичное отклонение |
| FAIL | Ожидание нарушено при достаточных возможностях стенда |
| SKIP | Проверка неприменима или явно не включена |
| BLOCKED | Проверка требовалась, но недостаёт capability, fixture или артефакта |
| ERROR | Внутренняя ошибка KEEMU или инфраструктуры, мешающая достоверному результату |

Для каждого результата: cause_class (package/environment/harness/unknown), evidence, mode (real/shim/static), required, длительность и ограничения. Причину unknown нельзя автоматически переклассифицировать в дефект пакета.

Агрегация: ERROR → FAIL → BLOCKED → WARN → PASS. SKIP обязательного теста даёт BLOCKED. При отсутствии выполненных обязательных тестов PASS запрещён. В отчёте показывается coverage: required/passed/failed/blocked/skipped.

### 14.2. Exit codes

| Код | Значение |
|---|---|
| 0 | Все обязательные проверки PASS; WARN допустим только без --strict |
| 1 | Есть FAIL |
| 2 | Ошибка CLI, схемы или формата входного файла |
| 3 | ERROR среды исполнения или KEEMU |
| 4 | BLOCKED, включая обязательную неподдержанную архитектуру/capability |
| 5 | Только WARN при --strict |

Если статический test-case доказывает wrong architecture внутри пакета, это FAIL/1. Если запрошенный target вообще не поддержан стендом — BLOCKED/4. Если файл невозможно распознать как пакет — invalid input/2.

### 14.3. Содержимое отчёта

Каталог reports/<UTC-timestamp>-<run_id>/:

- report.json, report.md, resolved-scenario.yaml, lock.json.
- operation-log.jsonl; stdout/stderr по операциям.
- ndmc.jsonl, events.jsonl, список подмен.
- filesystem-before.json, filesystem-after.json, filesystem.diff.json.
- installed-packages.txt, processes.json, sockets.json, network.json.
- traces/ и pcaps/ только для сценариев, которые их включили.

В JSON: schema_version, run_id, итог, проверяемый артефакт и hash, scenario hash, profile revision, git commit и dirty flag KEEMU, OCI digest, QEMU version, binfmt configuration, host kernel, Entware target, feed lock, runtime versions, capability results, network fidelity, coverage, список checks.

Filesystem snapshot хранит путь, тип, mode, uid/gid, hash файла или symlink target. /proc, /sys, /dev и изменяемые временные файлы исключаются по явному правилу. Остатки после удаления сравниваются с allowlist; сохранённый conffile не является автоматической ошибкой. Readable diff не должен раскрывать содержимое конфигураций с секретами.

Наблюдение процессов должно учитывать QEMU: comm/exe в /proc может относиться к эмулятору. Не определять сервис только через pgrep по имени приложения; использовать совокупность запуска, PID lineage, pidfile при наличии, сокетов и функциональной readiness.

Трассировка целевого приложения: QEMU_STRACE, с известными ограничениями. Нативный strace самого QEMU — отдельная диагностика хостовых вызовов. Target strace не является обязательным рабочим инструментом MVP.

## 15. Изоляция и ресурсы

Контейнер используется как граница изоляции; chroot сам по себе такой границей не считается. Для неизвестных пакетов рекомендуемая среда испытаний — отдельная VM. KEEMU не заявляет защиту от всех атак на общее ядро.

Обязательные ограничения:

- Не использовать --privileged, host network/PID и Docker socket внутри target.
- Не монтировать /, HOME, SSH/Git credentials и произвольные host-каталоги.
- Передавать входы read-only; разрешать только каталоги текущего run для результатов.
- Не выдавать SYS_MODULE; NET_ADMIN/NET_RAW только сетевому сценарию в собственном namespace.
- Не отключать весь seccomp/AppArmor ради обхода одной ошибки: сначала найти конкретный syscall и описать минимальное исключение.
- CPU/memory/PID limits и ограничение объёма логов; defaults: 2 CPU, 1 GiB RAM, 256 PID, 20 MiB на поток журнала с отметкой усечения. Это ограничения стенда, не модель ресурсов роутера.
- Отдельно контролировать место на диске; Docker memory limit не ограничивает writable layer. Проверять запас, ограничивать распаковку и останавливать run при установленном пороге заполнения.
- Интернет разрешать только сценарию установки, которому он нужен; тестовый LAN/WAN остаётся изолированным.

Все создаваемые контейнеры, сети и кеши маркируются. Cleanup удаляет только принадлежащие run ресурсы. Запретить docker system prune и глобальный сброс iptables как способ очистки.

## 16. Состояние, сбои и параллельные запуски

Состояния окружения: creating, installing, stopped, starting, running, stopping, failed, destroyed. Переходы сохраняются атомарно в JSON registry с блокировкой. Registry не заменяет проверку фактического состояния Docker.

При старте CLI сверяет labels контейнеров и registry. Прерванный run получает interrupted и частичный отчёт. Повторный cleanup безопасен; занятый порт, существующее имя и отсутствующий контейнер дают конкретное сообщение.

Матрица сначала выполняется последовательно. --jobs добавляется после проверки изоляции имён, сетей и отчётов. Блокировать одновременную мутацию одного persistent environment; разные окружения должны быть независимы.

Кеш индексируется по digest rootfs/target/версии схемы. Неполный кеш после прерывания не считается готовым. Сначала временный каталог, затем атомарное переименование. Persistent environment остаётся привязанным к исходному digest; изменение lock не обновляет его автоматически.

## 20. CI и разумный объём проверок

На обычное изменение: lint, schema/unit tests и затронутый integration test. Полную матрицу запускать при изменении rootfs/runtime/QEMU, перед релизом и по явному запросу. Не повторять неизменные тяжёлые проверки ради формального количества запусков.

Сетевые испытания требуют runner с подтверждёнными kernel capabilities и binfmt. Обычный CI runner не считать пригодным заранее. Разделить portable tests и privileged-setup network job; пакеты по-прежнему не запускаются в privileged контейнере.

Для pull request из недоверенного источника не выдавать секреты и доступ к чувствительному self-hosted runner. Полноценный network job выполнять в одноразовой VM или изолированном проверенном окружении.

Если окружение CI не позволяет тест, его статус BLOCKED/SKIP по применимости. Это не равнозначно прошедшему релизному gate. Перед релизом обязательные acceptance ID должны иметь реальные результаты.

## 21. Правила работы исполнителя

Этот раздел предназначен для переноса в проектный AGENTS.md при начале разработки. Сейчас он является частью ТЗ и не означает, что программный проект уже создан.

### 21.1. Старт

1. Прочитать AGENTS.md, это ТЗ, progress, limitations, актуальные ADR и git status.
2. Если репозиторий существует, сначала определить его стек и сделанную работу; не создавать второй каркас рядом.
3. Составить краткий план ближайшего вертикального сценария. Начать с P0, а не с реализации всех команд CLI.
4. Проверить доступные инструменты и хост. Не предполагать root, Docker, Интернет или способность запуска контейнеров только по наличию терминала.
5. При отсутствии Docker-хоста выполнить полезную независимую работу: схемы, парсер, fixtures, отчёты. Явно отметить, какие интеграционные проверки не запускались.

### 21.2. Реализация

- Работать вертикальными срезами: реальный пакет → реальный запуск → проверка → отчёт.
- Выбирать простейшую реализацию, закрывающую текущий acceptance ID. Не создавать систему плагинов, универсальный workflow engine или отдельный daemon заранее.
- Любая подмена требует имени, причины, теста и записи в limitations/report.
- Не удалять обязательную проверку и не ослаблять assertion, чтобы получить зелёный отчёт.
- При ошибке сначала сохранить команду, exit code, версии и короткий лог; затем проверить наиболее вероятную причину.
- Не запрашивать повторное подтверждение обычных правок и проверок внутри согласованного проекта. Соблюдать реальные ограничения среды и полномочия пользователя.
- Не менять настройки физического роутера, firewall хоста, binfmt, доступность сервисов снаружи или облачную инфраструктуру молча.
- Зависимости закреплять по фактической установке. Не придумывать команды API, версии, hashes и результаты.
- Не заявлять поддержку модели Keenetic на основании generic AArch64/MIPS теста.

### 21.3. Продолжение между сессиями

В docs/progress.md после законченного среза записывать:

- текущий этап и git commit;
- что работает и чем подтверждено;
- acceptance ID и пути к отчётам;
- блокеры и уже проверенные гипотезы;
- оставшиеся изменения и следующий конкретный шаг;
- незавершённые ресурсы и способ безопасной очистки.

ADR создавать только для решений с последствиями: runtime/rootfs, стратегия firewall, NFQUEUE workaround, способы установки приложений, схема состояния. Не вести подробный пересказ каждого tool call.

Git commits делать небольшими и осмысленными в рамках разрешённого workflow. Не включать в коммит пользовательские посторонние изменения, секреты и runtime artifacts. Работа не должна зависеть от памяти текущего чата.

### 21.4. Завершение этапа

Показать результат, способ запуска, выполненные проверки и оставшиеся ограничения. Для незапущенного теста писать «не запускался», для блокера — точную причину и требуемую возможность. Не писать «готово», если созданы только файлы или прошёл лишь статический анализ.

## 22. Риски и решения при блокировке

| Риск | Как проверить рано | Допустимое решение |
|---|---|---|
| Binfmt/дочерние exec не работают | P0 shell → ELF → script | Исправить регистрацию или объявить хост неподдержанным |
| Target netlink/ABI несовместимы | NFQUEUE probe + native control | Явный ограниченный режим; 1C blocked до решения |
| Нет нужных модулей ядра | Doctor/capability probe | Другой Linux-хост/VM; не имитировать успешную загрузку |
| Пакет требует незадокументированный NDM | Inventory и strict shim | Получить точные fixtures; блокировать конкретный сценарий |
| Upstream загрузки меняются | Повтор установки по lock | Минимальное зеркало с hashes |
| Loopback web не публикуется | Probe внутри и снаружи | Штатный bind либо явный namespace proxy |
| QEMU и host tools маскируют архитектуру | ELF и PATH audit | Отделить native tools, фиксировать provenance |
| Рост объёма работ | Отсутствие законченного вертикального сценария | Завершить 1A, перенести удобства за MVP |

Не использовать полную эмуляцию прошивки как автоматический fallback внутри MVP. Это отдельный проект с другой стоимостью.

## 23. Оценка трудозатрат

Планировочная оценка для одного опытного разработчика с помощью ИИ и доступным Linux-хостом: P0 — 3–7 рабочих дней; MVP 1A — суммарно 4–6 недель от старта; весь MVP 1 — ориентировочно 8–12 недель. Диапазон не является гарантией и уточняется после P0.

ИИ ускоряет написание кода и анализ журналов, но не заменяет реальный запуск целевых бинарников, наблюдение событий Keenetic и проверку NFQUEUE. Существенная несовместимость QEMU или недокументированная интеграция приложения требует отдельной переоценки.
