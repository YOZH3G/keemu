# Limitations

## Current verified boundary

The P0 technical-risk gate has real AArch64 evidence for Docker/binfmt target execution, localhost-only HTTP/UDP publishing, and state persistence across service restart and Docker stop/start. Its NFQUEUE requirement is closed as a reproducible BLOCKED capability diagnosis, not an ACCEPT/DROP result. Exact inputs and report digests are in `docs/evidence/p0-evidence-manifest.md`.

## Known limitations

- Docker Engine 29.7.2 is reachable through a privileged host socket. The separately approved `qemu-aarch64` binfmt registration must be revalidated after reboot or runner change. No privileged target container or public port was used.
- P0-05 proves AArch64 target shell/opkg/child/shebang execution and bounded native-init signal/reaping behavior. It does not prove cross-target support or interruption/stale-resource recovery. The direct-shebang check used an explicitly executable disposable `/tmp` tmpfs because the baseline noexec tmpfs cannot run test files.
- P0-06 proves only the locked web-demo slice: explicit `127.0.0.1` TCP/UDP publishes, Docker-host-vantage HTTP/UDP observation through an explicitly approved constrained host-network observer, and persisted state. It is not a general `up`/`down` lifecycle implementation and does not expose a public service.
- The host observer is an evidence instrument, not an application or general network-runtime component. It had no mounts, privilege, published port, retained state, or host mutation path; it was owner-checked and removed after each observation.
- The NFQUEUE diagnostic did not bind a queue, install a rule, send a packet, produce a verdict, load a host module, or create a network topology. Native socket creation does not prove target NFQUEUE capability; the static target socket returned `EPROTONOSUPPORT`, and the original dynamic target consumer needs unavailable `GLIBC_2.34`.
- MIPSEL/MIPS have real SHA-256-locked 20-package roots, target GCC-built hello/web-demo/NFQUEUE fixtures, and audited mixed images with 31 target ELFs each. Direct QEMU/PRoot shell/opkg/nested/shebang/fixture diagnostics and bounded Docker/binfmt shell/opkg/nested/fixture argument checks now pass. The first Docker observation failed `exec /bin/sh: exec format error` on both; separate explicit approval added only the MIPS binfmt handlers and verified exact registration. Recheck those handlers after reboot/runner changes. `keemu init` and single-scenario `test` remain AArch64-only; matrix orchestration now exists but reports both MIPS cases BLOCKED, not PASS. A host-side strict NDM process shim now has synthetic-only portable proof, without target `/opt/bin/ndmc` installation, observed device bytes or package lifecycle integration; A11 remains BLOCKED as a whole ID. Event contracts, MIPS general lifecycle and network verdicts are not implemented. See `docs/evidence/m1b18-targets.md`, `docs/evidence/m1b19-matrix.md`, and ADR-0012. One-shot Docker diff is path/change metadata, not a byte-complete filesystem audit.
- Matrix v1 requires an explicit per-case `lock` in addition to the specification's illustrative profile/scenario pair, because the existing runnable lifecycle never accepts an unlocked scenario. Input/schema errors currently exit 2 without an A21 bundle; a valid but incomplete mapping produces a BLOCKED bundle. The aggregate records each child report path and SHA-256; MIPS cases have no child lifecycle report until supported. The matrix `profile`/`runtime` fields are aggregate placeholders, not a fabricated target profile or image provenance; use child reports for actual AArch64 metadata. `--strict` maps WARN-only results to exit 5, but cannot turn required BLOCKED cases into PASS.
- This worker namespace cannot read host `/proc/sys/fs/binfmt_misc`; both MIPS `keemu doctor` profiles still report binfmt BLOCKED/exit 4 despite separately verified host entry readback and passing actual target Docker execution. Do not infer doctor PASS from the runtime probe or Docker failure from the doctor visibility gap.
- Common `RunReport` schema-version-2 metadata and immutable bundle primitives exist, but most later runtime producers do not yet populate full lifecycle provenance.
- Input schemas and loaders prevent ambiguous keys, unsupported versions, unowned path traversal, and symlinked inputs at validation time. The one-shot runner uses no-follow input reads, rehashes staged bytes and verifies the Docker copy-back; other consumers still need use-time revalidation. The scenario lock loader checks local source/scenario hashes, while the runner checks profile/feed/base/image bindings; independent live QEMU/binfmt provenance is incomplete. Only exact `127.0.0.1` host binding is representable in the version-1 scenario, and the one-shot runner declines publishing. Public exposure requires separate approval.
- The m1a-11 `init` cache covers the locked AArch64 base only, not fixture installation or full cross-target A01/A19 acceptance. It requires staged local P0 artifacts plus a live Docker/binfmt runner for its first build; offline repeat requires the Docker-local image to remain present. The pinned public feed URL in `/opt/etc/opkg.conf` identifies origin but is not a content-addressed upstream snapshot: `init` never invokes `opkg update`, and one-shot `test` installs only a hash-verified local IPK. Installed-time fields are normalized to zero for repeatable bytes; Docker COPY removes BusyBox's setuid bit, explicitly recorded in the image audit. The recorded `oci_digest` is the local Docker image ID, not a registry manifest digest. Target DNS passed inside the bridge container; HTTPS checked only from the Hermes process namespace with default CA/hostname validation because pinned BusyBox wget lacks TLS. Do not misreport this as target HTTPS. Cache input pathname race hardening for untrusted writable directories and full interruption recovery remain later work.
- The m1a-13 `test` runner uses a disposable target BusyBox gzip link because the immutable base lacks one. It compares Docker diff path metadata after removal with explicit residual allowances; it does not prove file-content identity, full socket/process closure, or cleanup after process crash/SIGKILL. Real failures retain the primary stage and a separately assessed cleanup status. Host publish, target HTTPS/UDP and other architectures are not covered.
- The m1a-14 persistent path pins a local AArch64 IPK, records owner-checked Docker identity before install, and refuses replacing names, input snapshots or Docker IDs. It accepts only target-loopback HTTP readiness without host publication or added capabilities. It does not run all scenario checks, expose an extra-package `install` command, or create the one-shot runner's JSON/Markdown/JSONL bundle for persistent failures. An m1a-16 real SIGKILL test verified explicit owner-only recovery/retry at the pre-ID and post-start stages, but this requires a separate `recover --yes` invocation: normal CLI start does not auto-repair. It discards uncertain installation/service state rather than replaying postinst; it does not emit a schema-version-2 partial report, cover one-shot SIGKILL, network-resource crashes, an untrusted same-UID actor, a full socket census or a hard disk quota. A same-UID adversary racing the owner-only registry path is outside the cooperative flock guarantee.
- The m1a-15 AArch64 TLS frontend is a separate fixture component in an immutable P0 web-demo image; it does not turn generic `keemu test`/`up` into a host-published HTTPS/UDP lifecycle. A disposable, bounded host-network observer tests only Docker-host loopback; the target never joins the host network. TLS trust exists only in that observer's local CA context, not target BusyBox or the host's global store. SDK archives are SHA-256-pinned local build inputs; an offline repeat needs those archives and the existing Docker-local images. Ephemeral host ports can change after Docker restart and must be read back. No private keys are tracked. General persistent report bundles and full A02–A09/A19 acceptance remain unproven.
- PRoot is not a security or container-isolation boundary. A generic AArch64 result does not establish compatibility with a Keenetic model or KeeneticOS release.

## Truthfulness rule

The m1a-17 ledger in `docs/evidence/m1a17-acceptance.json` freezes a project-clean but shared-host AArch64 Docker/binfmt run, not a clean-Ubuntu installation. All A01–A09 and A18–A21 whole IDs were BLOCKED **at that observation** for listed gaps even though their AArch64 slices passed. MIPS/MIPSEL and fresh-Ubuntu were SKIP in that historical ledger; m1b-18 first recorded Docker/binfmt BLOCKED and subsequently added separately authorized MIPS handlers, producing new hash-bound PASS evidence on both targets. Together with the prior AArch64 proof, the A01 three-generic-target ELF/shell/nested-exec check is now PASS; this is not retroactive modification of the m1a-17 ledger. The earlier ignored MIPS failure probe bytes were overwritten by the approved host remediation and are unavailable; the historical ledger digest is retained, while current PASS raw bytes are tracked in Git. Other ignored raw JUnit/reports require local retention to recheck their SHA-256. Wrong-architecture and shebang package reports correctly FAIL at inspection. No network acceptance is inferred.

P0 completion means its four technical-risk conditions have evidence or an explicit reproducible blocker. It is not a claim that every acceptance ID is PASS, that NFQUEUE ACCEPT/DROP works, or that MVP 1 is complete. Missing checks remain NOT RUN, PARTIAL, or BLOCKED as shown in `docs/traceability.md`.
