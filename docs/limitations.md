# Limitations

## Current verified boundary

The P0 technical-risk gate has real AArch64 evidence for Docker/binfmt target execution, localhost-only HTTP/UDP publishing, and state persistence across service restart and Docker stop/start. Its NFQUEUE requirement is closed as a reproducible BLOCKED capability diagnosis, not an ACCEPT/DROP result. Exact inputs and report digests are in `docs/evidence/p0-evidence-manifest.md`.

## Known limitations

- Docker Engine 29.7.2 is reachable through a privileged host socket. The separately approved `qemu-aarch64` binfmt registration must be revalidated after reboot or runner change. No privileged target container or public port was used.
- P0-05 proves AArch64 target shell/opkg/child/shebang execution and bounded native-init signal/reaping behavior. It does not prove cross-target support or interruption/stale-resource recovery. The direct-shebang check used an explicitly executable disposable `/tmp` tmpfs because the baseline noexec tmpfs cannot run test files.
- P0-06 proves only the locked web-demo slice: explicit `127.0.0.1` TCP/UDP publishes, Docker-host-vantage HTTP/UDP observation through an explicitly approved constrained host-network observer, and persisted state. It is not a general `up`/`down` lifecycle implementation and does not expose a public service.
- The host observer is an evidence instrument, not an application or general network-runtime component. It had no mounts, privilege, published port, retained state, or host mutation path; it was owner-checked and removed after each observation.
- The NFQUEUE diagnostic did not bind a queue, install a rule, send a packet, produce a verdict, load a host module, or create a network topology. Native socket creation does not prove target NFQUEUE capability; the static target socket returned `EPROTONOSUPPORT`, and the original dynamic target consumer needs unavailable `GLIBC_2.34`.
- MIPS and MIPSEL artifacts and execution are untested. Strict version-1 scenario/production-lock/persistent-environment inputs, static IPK inspection, one-shot AArch64 application lifecycle and bounded persistent registry/CLI lifecycle exist, but matrices, NDM fixtures, event contracts and full acceptance runs are not implemented. One-shot Docker diff is path/change metadata, not a byte-complete filesystem audit.
- Common `RunReport` schema-version-2 metadata and immutable bundle primitives exist, but most later runtime producers do not yet populate full lifecycle provenance.
- Input schemas and loaders prevent ambiguous keys, unsupported versions, unowned path traversal, and symlinked inputs at validation time. The one-shot runner uses no-follow input reads, rehashes staged bytes and verifies the Docker copy-back; other consumers still need use-time revalidation. The scenario lock loader checks local source/scenario hashes, while the runner checks profile/feed/base/image bindings; independent live QEMU/binfmt provenance is incomplete. Only exact `127.0.0.1` host binding is representable in the version-1 scenario, and the one-shot runner declines publishing. Public exposure requires separate approval.
- The m1a-11 `init` cache covers the locked AArch64 base only, not fixture installation or full cross-target A01/A19 acceptance. It requires staged local P0 artifacts plus a live Docker/binfmt runner for its first build; offline repeat requires the Docker-local image to remain present. The pinned public feed URL in `/opt/etc/opkg.conf` identifies origin but is not a content-addressed upstream snapshot: `init` never invokes `opkg update`, and one-shot `test` installs only a hash-verified local IPK. Installed-time fields are normalized to zero for repeatable bytes; Docker COPY removes BusyBox's setuid bit, explicitly recorded in the image audit. The recorded `oci_digest` is the local Docker image ID, not a registry manifest digest. Target DNS passed inside the bridge container; HTTPS checked only from the Hermes process namespace with default CA/hostname validation because pinned BusyBox wget lacks TLS. Do not misreport this as target HTTPS. Cache input pathname race hardening for untrusted writable directories and full interruption recovery remain later work.
- The m1a-13 `test` runner uses a disposable target BusyBox gzip link because the immutable base lacks one. It compares Docker diff path metadata after removal with explicit residual allowances; it does not prove file-content identity, full socket/process closure, or cleanup after process crash/SIGKILL. Real failures retain the primary stage and a separately assessed cleanup status. Host publish, target HTTPS/UDP and other architectures are not covered.
- The m1a-14 persistent path pins a local AArch64 IPK, records owner-checked Docker identity before install, and refuses replacing names, input snapshots or Docker IDs. It accepts only target-loopback HTTP readiness without host publication or added capabilities. It does not run all scenario checks, expose an extra-package `install` command, or create the one-shot runner's JSON/Markdown/JSONL bundle for persistent failures. A failed postinst retains `failed` state and attempts owner-only cleanup; SIGKILL between Docker create and registry ID publication, uncertain cleanup, recovery/retry and a full process/socket census remain unverified. A same-UID adversary racing the owner-only registry path is outside the cooperative flock guarantee.
- PRoot is not a security or container-isolation boundary. A generic AArch64 result does not establish compatibility with a Keenetic model or KeeneticOS release.

## Truthfulness rule

P0 completion means its four technical-risk conditions have evidence or an explicit reproducible blocker. It is not a claim that every acceptance ID is PASS, that NFQUEUE ACCEPT/DROP works, or that MVP 1 is complete. Missing checks remain NOT RUN, PARTIAL, or BLOCKED as shown in `docs/traceability.md`.
