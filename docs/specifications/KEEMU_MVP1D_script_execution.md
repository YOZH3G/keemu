# KEEMU MVP — дополнение: запуск и проверка shell-скриптов

**Статус:** дополнение к текущему MVP KEEMU  
**Область:** выполнение пользовательских `.sh`-скриптов внутри целевого Entware-окружения KEEMU  
**Приоритет:** высокий  
**Цель:** добавить штатный, воспроизводимый и безопасный механизм запуска shell-скриптов с хоста внутри эмулируемого окружения KEEMU с фиксацией результата выполнения.

---

## 1. Назначение

KEEMU должен позволять пользователю передать локальный shell-скрипт и выполнить его внутри целевого окружения, соответствующего выбранному профилю Keenetic/Entware.

Проверка должна отражать фактическое выполнение скрипта в целевой пользовательской среде, а не только статический анализ его содержимого.

Результат выполнения должен быть пригоден как для ручной диагностики, так и для автоматизированного тестирования пакетов, установщиков, init-скриптов, сервисных скриптов и других компонентов Entware.

---

## 2. Основной пользовательский сценарий

Минимально необходимый CLI-интерфейс:

```bash
uv run keemu script ./test.sh --profile generic-aarch64
```

Допустимая альтернативная форма для уже поднятого persistent-окружения:

```bash
uv run keemu exec demo --script ./test.sh
```

Первая форма должна быть основной для одноразовой проверки скрипта. Вторая может быть реализована как расширение существующего `keemu exec`.

---

## 3. Функциональные требования

### 3.1. Приём входного файла

KEEMU должен:

- принимать локальный `.sh`-файл как явный вход;
- проверять, что путь разрешён политикой host input paths KEEMU;
- запрещать неявный выход за пределы разрешённого project root;
- запрещать специальные файлы, устройства, FIFO и иные неподдерживаемые типы входов;
- безопасно прочитать файл до начала выполнения;
- вычислить SHA-256 исходного скрипта;
- зафиксировать хеш в отчёте;
- повторно проверить неизменность входного файла непосредственно перед копированием в target environment.

Изменение файла между валидацией и запуском должно приводить к `BLOCKED`, а не к продолжению выполнения.

### 3.2. Доставка скрипта в target environment

KEEMU должен копировать проверенный файл во временную область целевого окружения, например:

```text
/opt/tmp/keemu-script-<sha256-prefix>.sh
```

Требования:

- имя target-файла должно формироваться самим KEEMU;
- путь не должен зависеть от исходного имени файла;
- файл не должен перезаписывать существующий объект;
- перед выполнением должна быть проверена целостность скопированного файла;
- SHA-256 target-копии должен совпадать с SHA-256 входного файла;
- временный файл должен удаляться при штатном завершении и при ошибке, если cleanup безопасно возможен.

### 3.3. Выполнение

Базовый способ запуска:

```text
/bin/sh /opt/tmp/keemu-script-<hash>.sh
```

KEEMU не должен полагаться на executable bit или shebang для базового режима.

Дополнительно может поддерживаться direct/shebang execution как отдельная проверка совместимости, но она не должна заменять базовый `/bin/sh`-режим.

Запуск должен происходить внутри целевого окружения KEEMU через существующий runtime-механизм, а не через shell хоста.

### 3.4. Аргументы скрипта

CLI должен поддерживать передачу аргументов:

```bash
uv run keemu script ./test.sh --profile generic-aarch64 -- arg1 arg2
```

Аргументы должны передаваться как отдельный argv-массив без дополнительной shell-интерпретации.

Необходимо сохранить существующие ограничения KEEMU на:

- количество аргументов;
- максимальную длину аргумента;
- запрет NUL-байтов;
- общий ограниченный размер команды.

### 3.5. Рабочая директория

По умолчанию рабочая директория должна быть определена явно и воспроизводимо.

Рекомендуемое значение:

```text
/opt
```

Дополнительно должен поддерживаться параметр:

```bash
--cwd /opt/etc
```

Разрешены только target paths, прошедшие существующую валидацию KEEMU.

### 3.6. Переменные окружения

Для MVP допускается один из двух вариантов:

1. полный запрет пользовательских переменных окружения;
2. поддержка только явно перечисленных несекретных переменных через ограниченный интерфейс.

Рекомендуемый вариант для первой реализации — запрет произвольного host environment inheritance.

KEEMU не должен автоматически передавать в target:

- переменные окружения хоста;
- токены;
- ключи;
- proxy credentials;
- SSH-related environment;
- Docker-related environment.

### 3.7. Таймаут

Должен поддерживаться ограниченный timeout:

```bash
--timeout 60
```

Требования:

- значение по умолчанию: 60 секунд;
- минимальное значение: 1 секунда;
- максимальное значение должно соответствовать существующим ограничениям runtime KEEMU;
- превышение timeout должно фиксироваться как отдельный результат выполнения;
- зависший дочерний процесс не должен оставаться бесконтрольно работать после завершения проверки.

### 3.8. stdout и stderr

KEEMU должен раздельно фиксировать:

- `stdout`;
- `stderr`;
- признак усечения каждого потока;
- код возврата;
- факт timeout;
- длительность выполнения.

Должны применяться существующие bounded-output ограничения KEEMU.

Усечение вывода не должно скрываться: отчёт обязан явно указывать `truncated_stdout` и `truncated_stderr`.

### 3.9. Exit code

Результат запуска должен содержать реальный exit code скрипта.

По умолчанию успешным считается:

```text
exit_code == 0
```

CLI должен завершаться ненулевым кодом, если проверяемый скрипт завершился с ненулевым кодом, если только пользователь явно не задал другое ожидаемое значение.

Должен поддерживаться параметр:

```bash
--expect-exit-code 0
```

---

## 4. Assertions

Одноразовый script runner должен поддерживать минимальный набор проверок результата.

### 4.1. Exit code

```yaml
expect:
  exit_code: 0
```

### 4.2. stdout

```yaml
expect:
  stdout_contains:
    - "Installation completed"
```

### 4.3. stderr

```yaml
expect:
  stderr_not_contains:
    - "fatal"
    - "segmentation fault"
```

### 4.4. Файлы

```yaml
expect:
  files:
    - path: /opt/etc/example.conf
      exists: true
```

Для первой реализации обязательным является только `exit_code`.

Проверки stdout/stderr/filesystem могут быть реализованы в той же итерации, если не нарушают ограниченный scope MVP.

---

## 5. Интеграция со scenario format

Существующий `CommandCheck` должен оставаться основным механизмом проверки команд внутри scenario-based lifecycle.

Дополнение должно позволить использовать staged script как отдельный тип входа сценария либо как специализированный check.

Рекомендуемый вариант расширения схемы:

```yaml
checks:
  - id: run-installer
    kind: script
    path: ./fixtures/install.sh
    timeout_seconds: 60
    expected_exit_code: 0
```

Внутренне `script`-check может быть преобразован в безопасную последовательность:

1. validate host input;
2. hash;
3. stage;
4. verify target copy;
5. `/bin/sh <target-script>`;
6. collect result;
7. cleanup.

Не рекомендуется реализовывать `kind: script` простым преобразованием содержимого файла в `/bin/sh -c '<content>'`, поскольку это ухудшает воспроизводимость, диагностику, обработку размера и соответствие реальному файловому запуску.

---

## 6. Отчётность

Результат должен интегрироваться в существующий RunReport KEEMU.

Минимально должны фиксироваться:

```text
script source path
script SHA-256
target profile
target architecture
runtime/container identity
working directory
arguments
timeout
start/result status
exit code
stdout
stderr
stdout truncated
stderr truncated
duration
cleanup result
```

Пример JSON-фрагмента:

```json
{
  "script": {
    "source": "fixtures/install.sh",
    "sha256": "...",
    "target_path": "/opt/tmp/keemu-script-....sh"
  },
  "execution": {
    "interpreter": "/bin/sh",
    "argv": ["arg1", "arg2"],
    "cwd": "/opt",
    "exit_code": 0,
    "timed_out": false,
    "stdout": "...",
    "stderr": "...",
    "truncated_stdout": false,
    "truncated_stderr": false
  }
}
```

При scenario-based запуске результат должен попадать в обычные `report.json`, `report.md` и operation log согласно действующим правилам KEEMU.

---

## 7. Статусы результата

Следует сохранить общую семантику KEEMU.

### PASS

Скрипт был реально выполнен в целевом окружении и все обязательные проверки выполнены.

### FAIL

Целевая среда была доступна, но проверяемый скрипт или assertion завершились с фактическим несоответствием, например:

- неожиданный exit code;
- отсутствует ожидаемый файл;
- stdout/stderr не соответствует assertion.

### BLOCKED

Проверку невозможно корректно провести из-за отсутствующей capability или неподготовленного окружения, например:

- архитектура не поддерживается данным lifecycle;
- отсутствует требуемая kernel capability;
- скрипт требует недоступного NDMS API;
- входной файл изменился после validation;
- target image/lock не соответствует ожидаемому.

### ERROR

Ошибка самого harness или нарушение внутреннего контракта KEEMU.

Пропущенная или невозможная проверка не должна преобразовываться в `PASS`.

---

## 8. Архитектуры

### 8.1. AArch64

Для AArch64 функция должна использовать существующий проверенный Docker/binfmt runtime KEEMU.

Это основная обязательная архитектура для первой реализации.

### 8.2. MIPS/MIPSEL

Поддержка должна быть добавлена автоматически после того, как соответствующий generic lifecycle перестанет быть `BLOCKED`.

До этого команда должна возвращать корректный `BLOCKED`, а не пытаться запускать скрипт неподтверждённым способом.

Не следует создавать отдельную обходную реализацию script runner только для MIPS/MIPSEL, если она нарушает общий runtime contract.

---

## 9. Границы совместимости

Успешный запуск `.sh` в KEEMU подтверждает совместимость с доступной целевой userspace-средой KEEMU, но не является автоматическим доказательством полной совместимости с физическим Keenetic.

Особенно это относится к скриптам, использующим:

- `ndmc`;
- специфичные NDM API;
- Keenetic event hooks;
- kernel modules;
- NFQUEUE;
- netfilter-функции, отсутствующие в target runtime;
- реальные сетевые интерфейсы роутера;
- USB/модемное оборудование;
- GPIO;
- аппаратные watchdog/LED/button interfaces;
- проприетарные компоненты KeeneticOS.

Такие зависимости должны быть отражены через capabilities, fixtures, substitutions или `BLOCKED`.

---

## 10. Безопасность

Новая функция не должна ослаблять текущие ограничения KEEMU.

Обязательные требования:

- скрипт никогда не выполняется shell-ом хоста;
- Docker socket не передаётся внутрь target;
- запрещён `--privileged`;
- запрещён host PID namespace;
- запрещён прямой host network для package/script execution;
- запрещены host filesystem mounts вне явно разрешённого staging-механизма;
- запрещено наследование произвольного host environment;
- target container должен оставаться owner-labeled и проверяться существующими механизмами KEEMU;
- cleanup должен удалять только ресурсы текущего KEEMU run;
- не допускаются глобальные операции вроде `docker system prune`;
- при сомнении в ownership cleanup должен прекращаться, а состояние фиксироваться как requiring recovery.

---

## 11. Воспроизводимость

Для воспроизводимого режима должны быть зафиксированы:

- SHA-256 скрипта;
- profile ID и revision;
- target architecture;
- OCI image identity;
- используемый shell/interpreter;
- argv;
- cwd;
- timeout;
- дополнительные locked inputs, если они есть.

Повторный запуск с теми же locked inputs должен использовать те же входные данные либо возвращать `BLOCKED` при их изменении.

---

## 12. Persistent environment

Существующий `keemu exec` уже позволяет выполнять argv внутри persistent target environment.

Для MVP необходимо добавить удобный файловый слой поверх этого механизма:

```bash
uv run keemu exec demo --script ./test.sh -- arg1 arg2
```

Последовательность должна быть следующей:

```text
validate local script
        ↓
hash
        ↓
copy to owned running container
        ↓
verify copied bytes
        ↓
/bin/sh target-script args...
        ↓
collect exit/stdout/stderr
        ↓
remove staged script
```

Запуск разрешён только для среды в согласованном состоянии `running`.

---

## 13. Одноразовый режим

Для тестирования одиночных скриптов без предварительного `keemu up` рекомендуется отдельная команда:

```bash
uv run keemu script ./test.sh --profile generic-aarch64
```

Она должна:

1. проверить profile и locked runtime;
2. создать одноразовый owned container;
3. скопировать скрипт;
4. выполнить его;
5. провести assertions;
6. собрать отчёт;
7. выполнить cleanup;
8. удалить container и временные ресурсы.

Одноразовый режим предпочтителен для CI и regression tests.

---

## 14. CLI MVP

Минимальный интерфейс:

```text
keemu script SCRIPT
    --profile PROFILE
    [--timeout SECONDS]
    [--cwd TARGET_PATH]
    [--expect-exit-code CODE]
    [--repo PATH]
    [-- ARG...]
```

Пример:

```bash
uv run keemu script fixtures/install.sh \
  --profile generic-aarch64 \
  --timeout 120 \
  --expect-exit-code 0 \
  -- --force
```

## 15. Не входит в первую реализацию

Следующие функции можно оставить за пределами первой итерации:

- интерактивный TTY;
- stdin streaming;
- полноценная shell-сессия;
- выполнение произвольного bash-кода на стороне хоста;
- автоматическая установка отсутствующих interpreter/packages из сети;
- unrestricted environment injection;
- выполнение скриптов с host privileges;
- автоматическая эмуляция всех KeeneticOS API;
- автоматическое исправление несовместимых скриптов;
- полноценный syscall tracing;
- запись pcap для каждого запуска;
- performance benchmarking;
- запуск нескольких скриптов параллельно в одном target environment.

## 16. Acceptance criteria

Функция считается реализованной для MVP, если выполняются все следующие условия.

### A. Успешный скрипт

Скрипт:

```sh
#!/bin/sh
echo "KEEMU_OK"
exit 0
```

запускается в `generic-aarch64`, а отчёт содержит:

- правильный SHA-256;
- `exit_code = 0`;
- `KEEMU_OK` в stdout;
- отсутствие harness error;
- успешный cleanup.

### B. Ошибка скрипта

Скрипт:

```sh
#!/bin/sh
echo "expected failure" >&2
exit 7
```

должен:

- реально завершиться кодом `7`;
- сохранить stderr;
- при ожидании `0` дать `FAIL`;
- не превращаться в `ERROR` или `BLOCKED`.

### C. Timeout

Скрипт, превышающий заданный timeout, должен быть остановлен, а отчёт обязан явно показывать timeout.

### D. Аргументы

Скрипт должен корректно получать `$1`, `$2`, ... без shell-reparse аргументов на стороне хоста.

### E. Filesystem effect

Скрипт, создающий:

```text
/opt/tmp/keemu-script-test-result
```

должен позволять assertion проверить наличие файла.

### F. Input mutation

Если исходный `.sh` изменился после initial validation, но до target staging, запуск должен быть прекращён с `BLOCKED`.

### G. Cleanup

После одноразового запуска не должны оставаться:

- target script copy;
- owned test container;
- временные host staging files;
- иные unmanaged KEEMU resources.

### H. Host isolation

Тестовый скрипт не должен получать возможность выполнять команды непосредственно в host OS.

## 17. Рекомендуемая последовательность реализации

1. Добавить internal abstraction `ScriptInput`.
2. Реализовать secure read + SHA-256.
3. Добавить безопасный staging скрипта в container.
4. Реализовать `/bin/sh <script>` через существующий `DockerRuntime.exec()`.
5. Возвращать exit code, stdout и stderr.
6. Добавить timeout и bounded output.
7. Добавить cleanup staged script.
8. Добавить CLI `keemu script`.
9. Добавить `--script` к persistent `keemu exec`.
10. Интегрировать результат в RunReport.
11. Добавить `script`-check в scenario schema.
12. Добавить assertions по exit code и filesystem.
13. Добавить stdout/stderr assertions.
14. Добавить integration tests.
15. После появления общего MIPS/MIPSEL lifecycle распространить механизм на эти профили без отдельного runtime path.

---

## 18. Итоговое требование

KEEMU должен уметь не только устанавливать и запускать Entware-пакеты, но и выступать как воспроизводимый test harness для shell-логики этих пакетов.

Пользователь должен иметь возможность передать `.sh`-файл, выполнить его внутри выбранной целевой архитектуры, получить реальные `exit code`, `stdout`, `stderr` и эффекты на файловой системе, а затем однозначно классифицировать результат как `PASS`, `FAIL`, `BLOCKED` или `ERROR` в соответствии с действующей моделью KEEMU.
