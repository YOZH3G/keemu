# ADR-0010 — Explicit owner-checked recovery discards uncertain persistent state

Status: implemented and experimentally verified for m1a-16's bounded AArch64 persistent path; A18/A20 remain PARTIAL.

A crash cannot prove whether opkg postinst or a service transition completed. Do not resume/replay one automatically. `keemu recover NAME --yes` takes the existing per-name flock, reads the immutable registry identity, reconciles Docker's real owner/run/base/target labels and full IDs, and removes at most one run-owned container. If the registry has no ID because the creator died between Docker create and ID publication, require exactly the deterministic `/keemu-<run_id>` container name in addition to the matching labels/base. If an assigned ID still appears among all Docker containers but not in the owner-filtered result, it may be foreign/relabelled: refuse recovery. Refuse any extra owned container or owned network. Verify removal and Docker absence before transitioning through `failed` to the permanent `destroyed` tombstone. A failed removal leaves the original transitional/failed record for an explicit retry; an already destroyed record with no resources is idempotent. Healthy `running`/`stopped` records are never discarded by this command. Registry and Docker are not an atomic transaction, so this is cooperative owner-checked cleanup, not a same-UID hostile actor security boundary.

The opt-in `tests/integration/test_m1a16_recovery.py` invoked the actual persistent creator in a child and SIGKILLed it at two deliberate barriers: after real Docker allocation but before registry ID assignment, and after ID assignment/container start but before target install. It observed inconsistent read-only status and an exact one-run owner-labelled container, injected one removal failure and retried successfully, then verified idempotent tombstones and independent absence. A real Docker name collision and stale registry referring to a separate run-owned container were refused; a concurrent foreign-run bridge container/network stayed present and running during both recovery cycles. Read-only pre/post identity/state snapshots of non-KEEMU Hermes/Traefik containers and Docker networks matched. Live Docker inspect applied 2 CPU/1 GiB/256 PID, bounded JSON logs, cap-drop-all, no new privileges, no privileged/host-network/mount/port settings; target `/proc/1/status` reported `CapEff=0`, no Docker socket was visible, and the isolated target's TCP/UDP endpoint tables had no entries. Retained ignored evidence `.runtime/m1a16/m1a16-66c067937562.json` SHA-256 `895ef930d18519d6fa5d85092c195bb78db0735b1faa985def3f15f79de4b1e9`. Focused opt-in Docker suite (including existing one-shot command timeout, normal cleanup errors and persistent lifecycle): 13 passed; portable suite: 130 passed, 19 opt-in skipped.

Limitations: the recovery action is explicit, not automatic at CLI startup; it does not emit a schema-version-2 interrupted partial report. One-shot `test` lacks a durable per-run journal for SIGKILL recovery. No hard/continuous writable-layer or host disk quota exists; the 512 MiB observed threshold and Docker daemon log rotation do not supply one. This probe inspected TCP/UDP endpoints, not a complete Unix/raw socket/process/host syscall census. Out-of-band Docker resource-limit changes after creation are not continuously revalidated. Network-resource interruption belongs to the frozen 1C scope; no host firewall, kernel module, binfmt or foreign resource was mutated by this test. A18/A20 are not whole-ID PASS.
