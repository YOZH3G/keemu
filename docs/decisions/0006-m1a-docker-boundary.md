# ADR-0006 — MVP 1A Docker runtime boundary

Status: implemented for m1a-12; full A18/A20 acceptance remains partial.

The boundary in `src/keemu/docker_runtime.py` accepts only a full immutable Docker-local image ID and checks its project owner, target, native-init entrypoint and platform before creating a container. `docker` is invoked with an argv vector, never a host shell. Each container gets a fresh writable Docker layer; stopping and starting the *same* ID retains it, and a different ID starts clean. No bind mounts, declared volumes, Docker socket, host PID/network/IPC, privileged mode, added caps or published ports are admitted. Run-scoped bridge networks are labeled and checked independently. Container creation sets 2 CPUs, 1 GiB memory/swap, 256 PIDs, dropped capabilities, no-new-privileges, bounded tmpfs and a 20 MiB/single-file Docker JSON log driver, and reads back applied HostConfig. Default networking is none; a project-owned bridge may be passed explicitly. Image ID is a Docker-local content ID, not a registry manifest digest.

Mutation always targets a full ID and requires an immediate inspect of owner, run ID, resource kind, base ID and target. Network removal refuses attached containers. Reconciliation is read-only: it compares label-discovered, individually re-inspected Docker IDs with caller-supplied expected IDs and reports owned/unexpected/missing. It neither adopts nor removes an unexpected resource; an unowned or mislabeled expected ID is missing, not cleanup authority. This layer is intentionally independent of the atomic registry and lifecycle pipeline in later subtasks.

Command stdout/stderr are read concurrently with deadlines and byte caps. `logs()` limits each retrieved stream to 20 MiB and adds a truncation marker when that retrieval cap is exceeded. Docker's own single-file rotation can discard older records without a detectable marker: reports must not assert complete history from `docker logs` alone. Writable layer size is checked using `docker inspect --size` before start and before/after target exec; an observed 512 MiB threshold stops the owned container. This is not a hard or continuous disk quota, and host free-space cannot be reliably observed through this Docker socket. The run policy must separately budget and monitor filesystem capacity before running untrusted workloads. No claim of whole-host disk safety or complete interruption recovery follows from this boundary.

The opt-in live test `tests/integration/test_docker_runtime.py` exercised the exact m1a-11 locked image on Docker Engine 29.7.2: project-only bridge/container creation, HostConfig readback, AArch64 shell write/read, stop/start persistence, fresh-layer isolation, foreign-run cleanup refusal, owner-checked container/network removal and absence. Ignored evidence: `reports/m1a12-8055e7faa94b-docker-boundary.json`, SHA-256 `d56d3e156876a139c970fda7b72259dc150a1317d8649fa2cabbba7fdf240bf4`. This is a runtime-boundary test, not application lifecycle acceptance or an interruption injection test.
