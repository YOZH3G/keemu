# ADR-0016 — Extend the locked P0 consumer for network-demo (m1c-24)

Status: built and bounded-smoke-tested; target queue startup BLOCKED. Do not infer A14/A17 verdicts or MVP 1C completion.

The historical P0 NFQUEUE consumer source and its SHA-256 remain unchanged. The new static AArch64 `network_demo.c` compiles that source into the same translation unit and uses its queue configuration, packet decoder, verdict sender and counters. It adds HTTP API/UI, atomic mode-file updates, queue-ACK startup checks, and per-packet mode reload. The static binary, original source, new source, build recipe and inherited toolchain are bound by `locks/m1c24-network-demo-aarch64.json`. An explicit `--api-only` diagnostic serves API/UI with `queue_ready=false` and HTTP health 503; it cannot be mistaken for packet evidence. Production startup refuses API readiness until target queue bind/copy ACKs succeed. Malformed mode input is rejected; a missing/invalid mode file fails closed. Counters are process-local and not claimed persistent; selected mode lives in `/opt/etc/network-demo/mode` on the target writable layer.

`src/keemu/network_demo.py` contains fixture-only install/start/stop/remove and exact-rule hooks on an existing m1c-23 topology. It stages a SHA-256-checked static ELF, hashes the target copy, preserves mode across service stop, refuses to add a rule unless target API reports queue ready, and removes only a marked rule on stop. The requested rule targets client LAN `/32` → server WAN `/32`, TCP destination port 8080, FORWARD, queue 42; no queue-bypass. Control/UI/health bind router LAN port 9090 and cannot match the dedicated forwarded data-flow rule. No host publish or host iptables call occurs. `fixtures/network-demo/scenario.json` records the fixture contract; it is not a generic schema-v1 network scenario or IPK lifecycle.

Native API-only subprocess test verified GET state/UI, POST mode validation, atomic file state and service restart; no native queue was used. Real AArch64 topology smoke installed the locked binary, read its API from the client in explicit API-only mode, verified rule installation refused when queue is unavailable, then attempted a real target queue startup. It failed with `network-demo NFQUEUE: Protocol not supported` and no HTTP listener, rule, packet or verdict. Owner-checked cleanup left no project-owned Docker resource; foreign container/network IDs matched pre-run. Tracked raw evidence `docs/evidence/m1c24-network-demo-raw.json` matches ignored `reports/m1c24-ce8bd467f384-network-demo-smoke.json` byte-for-byte, SHA-256 `f36913458d18c5ec4a2d2dcf5d1ad859bdabcd09cb2ee88fd707ef17cc5d0006`. The lock SHA-256 is `a67805db40dff17ea35f9651e1e050166b14610eab60020f2f2b6e6d2e92cf7d`.

This subtask does not prove target API writes across container restart (m1c-25), nor ACCEPT/DROP or counters in the kernel (m1c-26). The target iptables backend and NFQUEUE extension were not verified; no module load or host firewall change is authorized. Treat A15/A16 as partial fixture slices only; A14/A17 remain BLOCKED.
