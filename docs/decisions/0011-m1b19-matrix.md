# ADR-0011 — Strict locked matrix orchestration does not promote target probes

Status: accepted for m1b-19 on 2026-09-24.

A runnable case requires an explicit production scenario lock; the illustrative profile/scenario matrix in specification §6.4 omits this existing lifecycle prerequisite. Matrix schema v1 therefore requires a per-case `lock` path. It verifies bounded input syntax, one logical package, unique profiles, scenario/profile/lock/source binding and target applicability before starting any child. Missing required generic targets are BLOCKED, not an implicitly smaller successful matrix. A valid locked IPK with actual control or ELF architecture mismatch is package FAIL/exit 1 even when another case is unsupported; malformed input is exit 2 before Docker; unsupported target lifecycle is environment BLOCKED/exit 4. Common report priority remains ERROR → FAIL → BLOCKED → WARN → PASS and `--strict` maps a WARN-only result to exit 5.

Execute cases in declared order through the existing one-shot runner only where it supports the target. Preserve each child report independently; the parent write-once schema-version-2 report records required case status, mode, cause, child path and SHA-256, plus resolved matrix bytes. No artificial Docker/container invocation is made for MIPS/MIPSEL: their locked rootfs/fixture and binfmt probes establish A01 target execution, not a general IPK install/remove lifecycle. The live m1b-19 observation is consequently aggregate BLOCKED with a real AArch64 PASS and two required static BLOCKED cases. It does not close A10 or MVP 1B.

Limitations: invalid matrix/schema input exits 2 without an A21 failure bundle; parent report aggregate profile/runtime are placeholders (not a target image). No parallel execution, automatic crash resumption, MIPS lifecycle, NDM or events are implied. Child lifecycle continues to revalidate use-time inputs and owner-gate cleanup; parent source-lock preflight does not authorize a later changed file.
