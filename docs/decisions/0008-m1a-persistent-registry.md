# ADR-0008 — Persistent environments use per-name locks and immutable identities

Status: implemented for m1a-14; A03–A06/A18 remain PARTIAL as whole acceptance IDs.

A registry entry lives under `.runtime/registry/<name>/` and retains a schema-version-1 JSON state and a SHA-256-bound scenario snapshot. Creation refuses any existing name, including an incomplete directory or destroyed tombstone. Registry directories are opened component-by-component from `/` with `O_NOFOLLOW`; missing components are created through directory FDs, so a symlinked `.runtime` or registry ancestor is rejected instead of redirecting state outside the project. A dedicated, owner-only flock file serializes one name across CLI processes while leaving distinct names independent. The registry writes complete 0600 temporary files, fsyncs them, publishes new entries without replacement, and atomically replaces state only after a locked read/compare of bytes and inode. Transitions reject changing scenario/profile/lock/image/run/resource identity. Missing, symlinked, altered, or partially created entries fail closed; a destroyed name is never reused. This is cooperative interprocess locking in an owner-only project directory, not protection against a malicious process with the same Unix identity that actively races path replacement.

`keemu up --scenario FILE --lock FILE --name NAME` accepts only a locally pinned AArch64 IPK with no host publish, extra capability, NDM fixture, secret environment, or non-target-loopback HTTP service probe. Scenario and profile models are parsed from the exact bounded, no-follow bytes later hashed into registry identity; replacement between parsing and hashing fails closed. Path-based YAML readers cap the read before allocation. The locked init-cache key must be exactly 64 lowercase hex characters, and its resolved rootfs must remain under the project init-cache before static inspection. The operation inspects a private IPK copy, offline-verifies the base and local image, hashes target copy-back, then uses real target opkg and checks inventory/files. The registry records `creating` before Docker create and the exact owner-labeled full container ID before install. Normal create failure attempts only run-owned cleanup and retains a `failed` record. Subsequent `up --name`, `down`, `restart`, `status`, `ports`, `logs`, `exec`, and `destroy` require a name and reconcile the recorded full ID with Docker labels, base ID, run ID and actual state. Transitional registry states are always reported inconsistent and require recovery. `destroy` requires a stopped container and retains a tombstone. Scenario service start/stop uses the frozen snapshot, target-loopback readiness and the same container across restart. Service start/stop failure retains `failed` and refuses further mutation, but does not automatically remove the persistent container; owner-checked recovery is a later task. No registered Docker resource is adopted by name or cleaned from an unverified registry claim.

Real opt-in Docker/binfmt tests exercised CLI creation, target hello execution, same-container restart, down/up with a postinst counter still equal to one, tombstone refusal, web-demo service readiness across restart/down/up, and failed postinst owner-checked cleanup with a retained `failed` registry state. Portable tests exercise same-name contention, independent names, symlinks, identical-byte inode replacement, stale writes, invalid transitions, foreign Docker-label refusal, and malformed CLI input. Tests do not prove process-kill recovery or that a failed cleanup can be retried automatically. Persistent CLI failures do not yet publish the one-shot runner's JSON/Markdown/JSONL report bundle; the registry state/error and read-only reconciliation are the only persistent-operation diagnostics in this slice. No host publishing, HTTPS/UDP, MIPS/MIPSEL, full service/socket census, automatic stale-state repair, SIGKILL recovery, or full acceptance is inferred.
