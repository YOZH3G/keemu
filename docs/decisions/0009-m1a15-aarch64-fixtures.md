# ADR-0009 — AArch64 HTTPS and host-vantage fixture evidence

Status: m1a-15 fixture slice verified on 2026-09-24; general lifecycle and full acceptance remain PARTIAL.

The existing immutable P0 AArch64 web-demo image is reused for HTTP and UDP. A separate static AArch64 OpenSSL TLS frontend forwards only bounded `/health` and `/state` request lines to the web-demo on target loopback. It is a separate fixture component, not a claim that the web-demo itself implements TLS. The binary is rebuilt from the repository source using the P0 locked cross-toolchain and three hash-checked arm64 SDK archives staged in ignored `.runtime/m1a15/`. `locks/m1a15-https-frontend-aarch64.json` binds the exact source, offline-only recipe, binary, SDK archive hashes/origins, web image and local Docker observer image ID. No SDK fetch occurs during the offline recipe. The static linker warns about dormant glibc `dlopen`/name-resolution references; the live fixture uses numeric addresses and completed TLS handshakes in the target.

The opt-in test creates a local CA and 24-hour server certificate in an owner-only ignored runtime directory; private keys are removed after owner-checked cleanup. It neither commits a private key nor modifies host trust. The client creates an isolated trust context from the generated CA and checks both DNS `localhost` and IP `127.0.0.1` names. An untrusted default CA and wrong hostname are explicitly rejected. The TLS service runs inside a bounded, nonprivileged AArch64 target container and reads its key as the file owner. Target ports 8080/tcp, 8443/tcp and 8081/udp are published only on Docker-host `127.0.0.1` with daemon-assigned host ports. The host observer is a disposable, run-ID-labeled, read-only, cap-drop-all, no-mount/no-publish Python process in the Docker host network namespace; it tests precisely those published ports and is removed by checked full ID. This vantage is explicit and distinct from the earlier target-namespace-only TLS probe. This is not a general host-network runtime permission for user packages.

The fixture writes state through HTTPS, verifies HTTP/HTTPS/UDP from host loopback, restarts both services in the same container, stops/starts the same container, re-reads persisted state and checks protocols again. Docker may allocate different ephemeral host ports after container restart; the test reads back the new actual ports before observing again. The independent one-shot hello test repeats the same scenario/IPK bytes twice against the offline-verified immutable base, checks each real opkg install, postinst-once, executable, removal, residual result, JSON/Markdown report and owner cleanup. The baseline A04/A05/A06 negative fixtures remain in `tests/integration/test_lifecycle.py` and `tests/unit/test_ipk_inspect.py`. No target trusted-CA store is changed: trust exists only in the observer's client context, and target BusyBox wget still does not support HTTPS.

Limitations: web-demo TLS/publish is a fixture-specific Docker probe, not yet wired to the general `keemu test` or persistent `keemu up` scenario lifecycle. Existing generic commands still reject host publish/HTTPS/UDP; their statuses must not be promoted from this test. The P0 image includes web-demo rather than installing the TLS fixture as an IPK. Persistent registry state and general service/socket census are not covered by the TLS test. The one-shot hello repeat proves prepared-local offline operation and byte-stable input reuse, not a hermetic Docker daemon or all architecture targets. Full A02–A09 and A19 acceptance remains PARTIAL except the explicitly bounded AArch64 fixture slices in traceability.
